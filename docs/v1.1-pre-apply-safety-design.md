# v1.1 Pre-Apply Safety Design

## Status

Design-only. `apply` remains disabled. This document and the accompanying schema define the safety contract that a future implementation must satisfy before any mutation path can be considered.

## Current evidence in this repository

The AgentOps CLI currently states that it manages repository governance records only and deliberately does not apply changes, read secrets, mutate runtime state, or orchestrate business work. The policy output also reports `apply_enabled: false`.

Existing verification already includes policy validation, proposal schema validation, diff hash binding, approval validation, diff path scope validation, optional Git clean checks, and optional patch applicability checks.

## External evidence

Git `apply --check` checks whether a patch would apply and turns off actual application. Git `apply` without `--check` applies a patch but does not create a commit. Git also rejects paths outside the working area by default unless unsafe path handling is explicitly requested.

GitHub rulesets / branch protection provide the repository-level enforcement layer for required checks and PR flow. Repository files and CI checks are guardrails; they are not substitutes for active GitHub enforcement.

JSON Schema Draft 2020-12 is used for structural validation of governance records and plans.

## Implemented in v1.1

- `schemas/pre-apply-plan.schema.json` defines the non-mutating pre-apply plan contract.
- `docs/examples/pre-apply-plan.example.yaml` provides a schema-valid example.
- `scripts/check-pre-apply-plan` validates plan files without applying patches or mutating profiles.
- CI runs the pre-apply plan validator.

## Non-goals

- Do not implement `apply`.
- Do not create locks.
- Do not write audit records.
- Do not create rollback commits.
- Do not mutate managed profile files.
- Do not read secret values.
- Do not mutate runtime state.
- Do not add business task routing.

## Pre-apply gates

A future apply implementation must fail closed unless all of these are true:

1. Policy is valid.
2. Proposal is schema-valid.
3. Approval records are schema-valid, unique, hash-bound, and meet the policy threshold.
4. No valid rejection record is present.
5. `diff.patch` hash equals `proposal.diff_sha256`.
6. All diff paths remain under the target profile scope.
7. Git working tree for the target profile is clean.
8. Patch applicability passes before mutation.
9. Operator explicitly confirms the plan.
10. An exclusive repository lock is acquired.
11. A rollback point is recorded.
12. Post-apply validation commands are defined.
13. Audit record capture is prepared.

## Attack / defense convergence

### Design point: schema before implementation

Attack 1: A future `apply` command could accrete hidden behavior not captured by docs.
Defense 1: Define a schema-valid pre-apply plan before implementing mutation.
Result: unchanged.

Attack 2: A plan schema could accidentally authorize mutation.
Defense 2: `mutation_enabled` is a required `false` constant in v1.1.
Result: unchanged.

Attack 3: A future contributor might treat the example plan as permission to apply.
Defense 3: The example, schema, script, and document all state that validation is read-only and `apply` remains disabled.
Result: unchanged.

Converged decision: define a read-only, non-mutating pre-apply plan contract first.

### Design point: lock model

Attack 1: Two apply attempts could race and produce interleaved state.
Defense 1: Future apply must require an exclusive repository-level lock.
Result: unchanged.

Attack 2: A stale lock could permanently block recovery.
Defense 2: The plan requires a stale timeout and manual recovery note.
Result: unchanged.

Attack 3: Automatically deleting stale locks could erase forensic evidence.
Defense 3: Failure recovery requires leaving lock evidence for manual inspection.
Result: unchanged.

Converged decision: future apply needs an exclusive repository lock with explicit stale handling and manual recovery evidence.

### Design point: rollback model

Attack 1: Applying without a rollback point leaves no reliable recovery route.
Defense 1: Future apply must record the pre-apply Git HEAD.
Result: unchanged.

Attack 2: Git working tree rollback alone might miss command output and validation evidence.
Defense 2: Audit requires stdout/stderr, exit codes, and git HEAD before/after.
Result: unchanged.

Attack 3: Partial mutation could continue after one failed gate.
Defense 3: Failure recovery requires aborting on first failure and rolling back partial mutation.
Result: unchanged.

Converged decision: use a Git-first rollback model plus audit evidence.

### Design point: Git patch semantics

Attack 1: `git apply --check` could be confused with actual application.
Defense 1: The current and v1.1 validators only use applicability checks; future mutation must be a separate explicit implementation.
Result: unchanged.

Attack 2: Unsafe paths could escape the repository/profile.
Defense 2: Existing diff path parsing rejects absolute, traversal, backslash, quoted, and non-normal paths, and v1.1 keeps path scope as a required gate.
Result: unchanged.

Attack 3: A patch may apply cleanly before but fail after unrelated changes.
Defense 3: Future apply must require a clean target scope and re-run applicability immediately before mutation.
Result: unchanged.

Converged decision: pre-apply must re-check clean state and patch applicability immediately before future mutation.

## Deep review checklist

- Safety boundary: `apply` remains disabled and returns non-zero.
- Schema safety: `mutation_enabled` is required and false.
- CLI safety: validation scripts are read-only.
- Policy safety: global forbidden actions remain enforced.
- Approval safety: threshold, duplicate approver, rejection, hash binding, and schema checks remain separate.
- Git safety: clean state and patch applicability are required future gates.
- Path safety: diff paths stay under `profiles/<agent>/`.
- Lock safety: future implementation requires one exclusive repository lock.
- Rollback safety: future implementation records pre-apply HEAD and supports Git-first rollback.
- Audit safety: stdout, stderr, exit codes, and git HEAD before/after are captured.
- CI safety: schema and example plan are validated in CI.
- Ruleset safety: GitHub rulesets remain the enforcement layer for `main`.
- Maintainability: schema, example, script, and doc are separate and reviewable.
- Rollback: revert the v1.1 PR to remove design assets without changing runtime behavior.
