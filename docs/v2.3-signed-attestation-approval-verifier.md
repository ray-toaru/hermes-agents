# v2.3 Signed Attestation Approval Verifier

## Status

Implemented as a read-only authenticated approval verifier slice. This does not enable real apply.

## Evidence Observed

ADR 0008 requires future mutation authority to verify approval evidence through live GitHub review evidence, cryptographically signed approval attestations, or another repository-enforced mechanism. Before this slice, the authenticated approval verifier had only `fixture_contract_only`; both `live_github` and `signed_attestation` failed closed. That left the project with an evidence contract but no non-fixture authenticated verification path.

## Implemented Changes

- Added `signed_attestation` mode to `scripts/verify-authenticated-approval`.
- Added `schemas/signed-approval-attestation.schema.json` for local Ed25519-signed approval/rejection attestation files.
- Added `schemas/trusted-approval-signers.schema.json` for reviewed public trust roots.
- Updated CI dependency installation to include `cryptography`, because Ed25519 verification is intentionally implemented through a reviewed crypto library rather than handwritten signature logic.
- Added tests covering:
  - successful signed approval evidence emission;
  - validation of emitted authenticated approval evidence;
  - `apply` remaining disabled after signed evidence is produced;
  - tampered signed payload failure;
  - signed rejection failure;
  - insufficient signer permission failure;
  - missing attestation failure;
  - `live_github` still failing closed.

## Signed Attestation Semantics

A signed attestation contains:

- a `payload` with repository identity, `change_id`, agent, exact `diff_sha256`, approver, identity subject, decision, signer key ID, and signing time;
- an Ed25519 signature over the canonical JSON encoding of the payload;
- no private key material.

A trusted signer policy contains only reviewed public trust roots:

- `key_id`;
- approver;
- identity subject;
- permission level;
- Ed25519 raw public key encoded as base64;
- explicit boundaries that the policy does not authorize apply or mutation.

The verifier accepts signed approval attestations only when all of the following hold:

1. the attestation schema is valid;
2. the signer key ID exists in the trusted signer policy;
3. the trusted signer policy schema is valid;
4. the Ed25519 signature verifies over the canonical payload;
5. repository full name and default branch match verifier arguments;
6. `change_id`, agent, and `diff_sha256` match the current proposal and diff;
7. trusted signer approver and identity subject match the signed payload;
8. decision is `approve`;
9. no valid signed rejection is present;
10. unique verified approvers meet `required_approvals`;
11. signer permission is at least `--minimum-permission`;
12. emitted authenticated approval evidence validates against `schemas/authenticated-approval.schema.json`.

The emitted authenticated approval evidence still requires:

```yaml
mutation_enabled: false
apply_authorized: false
status: verified_not_authorized
```

## Boundaries

This slice does not:

- implement `live_github` mode;
- contact GitHub or any external service;
- read private signing keys;
- read real secret values;
- mutate managed profile files;
- mutate runtime state;
- acquire or release real locks;
- execute rollback;
- create mutation audit records;
- authorize `hermes-agentops apply`;
- route or orchestrate business tasks.

## Attack / Defense Review

### Round 1

Attack: Signed attestation mode may be treated as apply authorization.

Defense: The emitted authenticated approval record still has `mutation_enabled: false`, `apply_authorized: false`, and `status: verified_not_authorized`. The `apply` command remains intentionally disabled and is tested after successful signed verification.

Status: Stable.

### Round 2

Attack: The repository could commit private signing keys or secret material.

Defense: The trust-root schema stores raw public keys only. Tests generate private keys inside temporary directories only. CI's existing secret guard rejects committed `*.pem`, `*.key`, `.env`, `secrets.json`, runtime databases, logs, sessions, and workspaces.

Status: Stable.

### Round 3

Attack: An attacker can edit unsigned fields outside the signed payload.

Defense: Authorization-relevant fields are all inside the signed payload. The signature is verified over canonical JSON of the payload. The outer document only carries schema version and signature metadata.

Status: Stable.

### Round 4

Attack: A valid signature from a trusted key can be replayed for another diff, branch, repository, or agent.

Defense: The payload binds repository full name, default branch, `change_id`, agent, exact `diff_sha256`, approver, identity subject, decision, signer key ID, and signing time. The verifier compares those values against the current proposal, current diff hash, trusted signer record, and verifier arguments.

Status: Stable.

### Round 5

Attack: A signed rejection could be ignored when enough signed approvals exist.

Defense: Any valid signed rejection for the change causes the verifier to fail closed before threshold success is emitted.

Status: Stable.

### Round 6

Attack: A low-permission signer could satisfy a future high-risk approval policy.

Defense: The verifier records permission from the reviewed trusted signer policy, not from the signed payload. `--minimum-permission` enforces a configurable lower bound and fails closed if the trusted signer is below it.

Status: Stable.

### Converged Decision

Implement signed attestation verification as a read-only authenticated evidence source using reviewed public trust roots and Ed25519 signature verification. Keep `live_github` fail-closed. Do not integrate signed evidence into mutation authority until lock lifecycle, rollback, audit capture, recovery, and integrated sandbox mutation pipeline designs are implemented and reviewed.

## Remaining Work

- Implement `live_github` mode as a separate read-only slice if direct GitHub review verification is required.
- Integrate authenticated approval evidence into a sandbox-only mutation pipeline before any real mutation proposal.
- Keep `hermes-agentops apply` disabled until all mutation prerequisite ADRs converge.
