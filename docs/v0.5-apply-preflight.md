# v0.5 Apply Preflight Gates

## Goal

Add non-mutating preflight validation for future apply workflows.

## Non-Goals

- Do not implement automatic apply.
- Do not mutate files from a change proposal.
- Do not read real secret values.
- Do not mutate runtime state.
- Do not add business task routing or workflow orchestration.

## Added Command

```bash
hermes-agentops changes verify <change-id>
```

## Verified Gates

The command validates:

- `changes/<change-id>/proposal.yaml` exists and matches `change-proposal.schema.json`.
- `changes/<change-id>/diff.patch` exists.
- proposal `diff_sha256` matches the actual `diff.patch` SHA-256.
- approval records match `approval-record.schema.json`.
- approval records point to the same change id and diff hash.
- rejection records block the change.
- distinct approvals meet the proposal threshold.
- affected paths stay under `profiles/<agent>/` for MVP.

## Why path scope is profile-only in MVP

A future apply workflow must not accidentally mutate CI, schemas, global policies, or runtime-facing files through a profile change record. MVP preflight limits proposed patches to `profiles/<agent>/` until broader path-risk inference exists.

## Apply Remains Disabled

`hermes-agentops apply` remains disabled and returns non-zero. Approval and preflight are necessary but not sufficient for execution.

Future apply still needs:

- authenticated approval identity
- Git clean/dirty gate
- file locking
- patch applicability check
- rollback point creation
- post-apply validation
- path-based risk inference
- policy-specific approval thresholds

## Attack Review

### Design point: preflight without apply

Attack: verification without execution is incomplete.
Defense: this is deliberate. v0.5 adds safety gates before adding any mutation path.
Change: none.

Attack: path scope blocks schema or policy changes.
Defense: schema and policy changes should continue through normal PR review, not profile-level change records, until path-risk inference is implemented.
Change: none.

Attack: approval identity is not cryptographic.
Defense: that is why apply remains disabled. v0.5 records and checks approvals but does not treat them as execution authority.
Change: none.

Conclusion: locked for v0.5.

## Review

- Secret safety: pass. No secret reads are introduced.
- Runtime safety: pass. No runtime mutation is introduced.
- Hermes runtime alignment: pass. This does not replace provider runtime, tools registry, session storage, gateway, cron, or AIAgent.
- Apply boundary: pass. Apply remains disabled.
- Long-term evolution: pass. Preflight gates are prerequisites for a future apply design.
