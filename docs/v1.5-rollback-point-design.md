# v1.5 Rollback Point Design

## Status

Design and read-only validation only. `apply` remains disabled.

This version does not create rollback points automatically, does not run `git reset`, does not run `git revert`, does not mutate managed profiles, and does not mutate runtime state.

## Implemented

- `schemas/rollback-point.schema.json`
- `docs/examples/rollback-point.example.yaml`
- `scripts/check-rollback-point`
- tests for valid and invalid rollback point records
- CI validation for the example rollback point

## Contract

A future rollback point must bind:

- `change_id`
- `agent`
- `pre_apply_commit`
- `current_head`
- `pre_apply_plan_sha256`
- `apply_lock_sha256`
- `strategy: git_first`
- `mutation_enabled: false`

The current contract requires `pre_apply_commit == current_head` because the rollback point is meant to be captured immediately before any future mutation begins.

## Safety boundary

The checker does not:

- implement or call `apply`;
- create rollback points;
- run rollback commands;
- mutate managed profiles;
- mutate runtime state;
- read real secret values;
- release or delete locks;
- execute business actions.

## Attack / defense convergence

### Design point: rollback point is evidence, not rollback execution

Attack 1: A rollback schema could be mistaken for permission to mutate and recover later.
Defense 1: `mutation_enabled: false` remains required and the checker is read-only.
Result: unchanged.

Attack 2: A rollback point could be reused for another change.
Defense 2: The validator requires `rollback_point_id == change_id + '_rollback'` and agent/change consistency.
Result: unchanged.

Attack 3: A rollback point could be detached from the plan or lock it protects.
Defense 3: The contract includes plan and lock SHA-256 bindings, with optional actual-file verification.
Result: unchanged.

Converged decision: rollback points are hash-bound evidence records, not recovery execution.

## Deep review checklist

- `apply` remains disabled.
- The checker is read-only.
- The schema requires `mutation_enabled: false`.
- The record binds change, agent, plan hash, lock hash, and commits.
- Optional evidence-file verification can bind hashes to actual plan and lock files.
- Rollback commands remain operator-reviewed future work.
- CI validates the example and negative tests.
