# v2.4 Integrated Sandbox Mutation Pipeline

## Status

Implemented as a sandbox-only evidence pipeline. It does not enable real apply.

## Implemented command

```text
scripts/run-integrated-sandbox-mutation <change_id>
```

The command copies reviewed repository governance inputs into a temporary workspace and executes the pipeline there only. Post-apply validation is now performed in the same temporary Git repository that acquired the temporary lock and created rollback-point evidence; it is not replayed in a second workspace.

```text
strict change verification
  -> authenticated approval verification
  -> pre-apply plan generation
  -> apply-lock analysis
  -> apply-readiness verification
  -> temporary-repository lock prototype acquisition
  -> temporary-repository rollback point evidence creation
  -> apply reviewed diff inside that same temporary repository
  -> same-sandbox post-apply validation
  -> integrated sandbox evidence emission
```

## Evidence contract

The run emits `schemas/integrated-sandbox-mutation-run.schema.json` evidence with:

- `sandbox_only: true`
- `mutation_enabled: false`
- `apply_authorized: false`
- source `profiles/` hash before and after the run
- per-step exit codes and stdout/stderr hashes
- artifact hashes for authenticated approval, pre-apply plan, lock analysis, readiness, temporary lock, rollback point, and post-apply validation
- an explicit `post_apply_validation_same_sandbox` assertion
- fail-closed failure stage

## Boundaries

The command never mutates source managed profiles, enables apply, releases locks, executes rollback, creates production audit records, reads secret values, mutates runtime state, or orchestrates business work.

The temporary lock, rollback point, patch application, and post-apply validation are deliberately created only inside the same throwaway sandbox repository. They are proof of sequencing and evidence compatibility, not production lock lifecycle integration or production validation.

## Root-cause note

During implementation, in-process script dispatch created Python bytecode caches under the temporary sandbox `scripts/` directory. The rollback point prototype correctly rejected this as a dirty working tree. The root cause was import side effects, not rollback logic. The fix disables bytecode writing during internal script dispatch and removes sandbox Python caches before clean-tree-sensitive phases.

## Review clarification

A prior implementation delegated post-apply validation to `scripts/run-post-apply-validation-sandbox`, which creates a second temporary workspace and therefore produced replay evidence. The integrated runner now applies `changes/<change_id>/diff.patch` directly inside its existing temporary repository after rollback-point evidence creation, then runs the allowlisted validation commands in that same repository. This fixes the evidence-chain semantics while still keeping all mutation sandbox-only.
