# v2.0 Apply Readiness Evidence Report

## Status

Implemented as a read-only evidence checker. This does not enable `apply` and does not declare any change executable.

## Purpose

The repository now contains several governance evidence layers. The apply readiness report gives a single aggregate view of whether those evidence records are present, missing, blocked, or future-only.

The key boundary is intentional: evidence completeness is not execution authority.

## Boundaries

The readiness checker must not:

- authorize apply;
- acquire or release real locks;
- mutate managed profile files;
- mutate runtime state;
- read real secret values;
- execute rollback;
- execute business actions;
- route or orchestrate business tasks.

`mutation_enabled` and `apply_authorized` must remain `false`.

## Gate Semantics

Required pre-apply gates currently include:

- `change_verify`;
- `approval_identity`;
- `pre_apply_plan`;
- `apply_lock_analysis`.

Each required pre-apply gate must appear exactly once with:

- `phase: pre_apply`;
- `required_before_apply: true`;
- a concrete `evidence_sha256` string;
- a safe relative `evidence_path` without absolute paths, traversal, or backslashes.

For `status: evidence_complete_not_authorized`, every required gate must be `status: present` and `blocking: false`.

For `status: blocked`, a required gate may be `status: blocked` with `blocking: true`. This represents evidence that blocks future apply consideration. It is still not apply authorization.

Future mutation-phase gates such as `apply_lock_record`, `rollback_point`, and `audit_record` may be represented as `future_only` because this repository still has no real mutation path.

`post_apply_validation` is a post-apply gate. It must not be treated as a pre-apply authorization requirement.

## Status Semantics

- `evidence_complete_not_authorized`: required evidence is represented and non-blocking, but apply is still not authorized.
- `incomplete`: required pre-apply evidence is missing or invalid.
- `blocked`: at least one gate blocks future apply consideration.
- `invalid`: the report itself is malformed or inconsistent.

## Future Use

A future apply command may use this report as one preflight input, but it must still have separate reviewed designs for authenticated approvals, atomic lock acquisition/release, rollback creation, actual mutation, post-apply validation, audit, and recovery.
