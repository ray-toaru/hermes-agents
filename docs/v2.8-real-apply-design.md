# v2.8 Real Apply Design Package

## Status

v2.8 adds a **design-only** real apply package. It does not implement, enable, or authorize real apply.

`hermes-agentops apply` remains disabled and must continue to return non-zero.

## Scope

The design package converts the v2.7 decision (`ready_to_design_real_apply: true`) into concrete design assets. It deliberately stops before mutation implementation.

Allowed in this slice:

- define the ordered future production pipeline;
- define production threat model and required mitigations;
- define recovery and lock-preservation runbook;
- validate that required design docs exist and carry boundary language;
- validate that `hermes-agentops apply` still fails closed.

Not allowed in this slice:

- profile mutation;
- runtime state mutation;
- secret reads;
- real lock release;
- rollback execution;
- production audit writing;
- feature flags that enable real apply;
- business orchestration.

## Design Contract

The structured contract requires:

```yaml
design_only: true
ready_to_implement_real_apply: false
ready_to_enable_real_apply: false
apply_must_remain_disabled: true
mutation_code_added: false
feature_flag_allowed: false
```

The checker enforces:

- schema validity;
- required design document paths are safe and exist;
- required boundary phrases are present in each design document;
- all required pipeline stages exist exactly in order;
- production blockers are recorded;
- `hermes-agentops apply` still returns non-zero with an explicit disabled/not-implemented message.

## Attack Review

### Attack: Use this design package as permission to implement real apply in the same PR

Rejected. The contract requires implementation and enablement flags to remain false, and `mutation_code_added` to remain false.

### Attack: Add a hidden feature flag to enable mutation

Rejected. The contract requires `feature_flag_allowed: false`, and the checker verifies `apply` remains disabled.

### Attack: Treat v2.4-v2.6 sandbox evidence as production evidence

Rejected. The design explicitly requires separate production lock, rollback, audit, validation, and recovery slices.

### Attack: Let a successful design contract imply production readiness

Rejected. A valid design contract only proves that the design package is internally consistent and non-authorizing.

### Attack: Release locks automatically after unknown failure to unblock future changes

Rejected. The recovery runbook requires unknown state to preserve locks and require manual review.

## Result

v2.8 changes the next safe step from “write real apply design” to “implement prerequisite production slices one by one while keeping apply disabled.”

Recommended next slice:

```text
production lock lifecycle integration, still disabled and non-mutating
```

## Test Runner Follow-Up

While validating v2.8, the combined rollback/audit/recovery/structured-command pytest group printed a passing summary but intermittently failed to return control to the shell in this interactive sandbox. The individual assertions were not failing: splitting that group into rollback/audit/recovery and structured-command validation groups returned cleanly with status 0.

The CI workflow now uses four explicit groups. This is a test-runner isolation change, not a safety-boundary change. It preserves full collected-test coverage while avoiding a post-summary process-exit stall in the sandbox-heavy tail of the suite.
