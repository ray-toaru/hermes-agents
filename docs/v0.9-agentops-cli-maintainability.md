# v0.9 AgentOps CLI Maintainability

## Goal

Improve reviewability of the AgentOps CLI before any future mutation path exists. This version must preserve the v0.8 safety boundary: `apply` remains intentionally disabled and returns non-zero.

## Why This Exists

PR #16 added apply-readiness gates and fixed trusted status reporting. Review also noted that the CLI implementation became compact and harder to audit. Before introducing any future mutation path, reviewers need a clear map of the current control flow and the intended semantics.

## Current Safety Boundary

AgentOps is still a management-plane tool only. It may validate governance files and write governance records under `changes/`, but it must not:

- implement automatic `apply`;
- mutate managed profile files from proposals;
- read real secret values;
- mutate runtime state;
- add business task routing or workflow orchestration;
- bypass Hermes provider runtime resolution;
- bypass Hermes tools registry or dispatch.

## Trusted Status Semantics

`changes list` and `changes show` must not display formal `approved` status from unchecked approval files.

The trusted status path should perform structural validation before deriving display status:

1. Validate policy shape and required defaults.
2. Load and schema-check the proposal.
3. Validate proposal `created_at` using explicit RFC3339-like validation.
4. Verify `diff.patch` hash binding.
5. Parse and normalize diff paths.
6. Validate approval records for schema, timestamp, `change_id`, `diff_sha256`, and duplicate approvers.
7. If structural validation fails, display `invalid`.
8. Only structurally valid records may contribute to displayed status.

This is intentionally separate from full `changes verify` threshold enforcement. Display commands need to show partially approved proposals without turning insufficient approval count into `invalid`.

## Verify Semantics

`changes verify` is stricter than display commands. It must fail closed when:

- `policy check` would fail;
- proposal schema or timestamp is invalid;
- `diff.patch` is missing or hash-mismatched;
- diff paths are malformed or outside the managed profile path;
- approval files are malformed, mismatched, duplicated, rejected, or hash-invalid;
- approval threshold is not satisfied;
- optional dry-run gates fail, such as Git clean check or `git apply --check`.

## Approve Semantics

`changes approve` writes a governance record, not an execution grant. It should:

- validate policy and proposal structure before writing;
- validate diff hash binding before writing;
- reject invalid approver names;
- validate the generated approval record against `approval-record.schema.json` before writing;
- not require the existing proposal to already satisfy approval threshold, because the first approval must be writable.

## Refactor Direction

Future refactoring should prefer explicit helpers and typed data flow over dense inline expressions. A useful target shape is:

- policy loading and validation helpers;
- proposal loading and schema validation helpers;
- diff path parsing helpers;
- approval record loading and validation helpers;
- trusted status calculation;
- full verify calculation;
- command functions with minimal business logic.

The refactor should be behavior-preserving and backed by the existing tests from v0.8.

## Apply Boundary

No part of this maintainability work authorizes implementation of `apply`. Before `apply` can be reconsidered, the project still needs authenticated approvals, repository-wide clean-state rules with explicit exclusions, file locks, rollback point creation, patch application sandboxing, post-apply validation, and branch protection or equivalent operational controls.
