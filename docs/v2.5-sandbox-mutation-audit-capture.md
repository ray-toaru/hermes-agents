# v2.5 Sandbox Mutation Audit Capture

## Status

Implemented as sandbox-only audit evidence.

This slice adds a read-only audit capture layer for integrated sandbox mutation runs. It does not implement real apply, write production audit records, mutate managed profiles, release locks, execute rollback, read secrets, mutate runtime state, or orchestrate business work.

## New Artifacts

- `schemas/sandbox-mutation-audit-record.schema.json`
- `scripts/generate-sandbox-mutation-audit`
- `scripts/check-sandbox-mutation-audit`
- `tests/test_sandbox_mutation_audit.py`

## Evidence Flow

```text
run-integrated-sandbox-mutation <change_id>
  -> integrated sandbox run evidence YAML
  -> generate-sandbox-mutation-audit <integrated-run.yaml>
  -> sandbox mutation audit evidence YAML
  -> check-sandbox-mutation-audit --integrated-run <integrated-run.yaml> <audit.yaml>
```

The audit generator consumes the integrated sandbox run evidence and records:

- repository and default branch labels;
- source Git head before and after audit generation;
- change ID, agent, operator, and integrated run ID;
- integrated run status and failure stage;
- source profile hashes before and after the sandbox run;
- authenticated approval evidence hash;
- readiness report evidence hash;
- temporary real-lock evidence hash;
- rollback point evidence hash;
- post-apply validation evidence hash, including failed same-sandbox validation evidence when validation fails after patch application;
- step-summary hash and redacted step metadata;
- recovery-required and manual-review flags.

## Boundary

The audit record has these fixed boundaries:

```yaml
sandbox_only: true
production_audit: false
mutation_enabled: false
apply_authorized: false
manual_review_required: true
```

The generator writes the audit record to stdout only. It intentionally does not write `changes/<change_id>/audit-record.yaml`, because that path is reserved for future production mutation auditing.

## Failure Semantics

A successful integrated sandbox run produces:

```yaml
status: success_recorded
recovery_required: false
```

A failed integrated sandbox run produces:

```yaml
status: failure_recorded
recovery_required: true
manual_review_required: true
```

The failure record is still valuable because it preserves hashes and stage evidence. It does not release locks, execute rollback, retry, or mark a change safe.

## Attack Review

### Attack: Treat sandbox audit as production audit

Rejected. The schema requires `production_audit: false`, `sandbox_only: true`, `mutation_enabled: false`, and `apply_authorized: false`. The checker rejects records that try to flip those flags.

### Attack: Use audit completeness as apply authorization

Rejected. Audit completeness records what happened in a sandbox. It does not prove live lock ownership, live rollback ability, or live repository mutation safety.

### Attack: Tamper with the integrated run after audit capture

Rejected when `check-sandbox-mutation-audit --integrated-run` is used. The checker validates the integrated run hash and key identity fields against the audit record.

### Attack: Use failed audit as recovery completion

Rejected. Failed sandbox runs require `recovery_required: true` and `manual_review_required: true`. The audit layer does not perform recovery.

### Attack: Hide command output details in audit

Accepted with constraints. The audit stores output hashes and step statuses, not raw logs, to avoid leaking sensitive content. Detailed integrated run evidence remains the primary evidence document.
