# v0.7 Change Workflow Hardening

## Goal

Address retrospective review findings from PR #4 and PR #6 before any future `apply` implementation.

## Non-Goals

- Do not implement automatic apply.
- Do not mutate runtime state.
- Do not read real secret values.
- Do not add business task routing or workflow orchestration.

## Changes

- Approval thresholds are loaded from `policies/global-permissions.yaml`.
- Change and approval schemas now use `format: date-time` for `created_at`.
- CLI schema validation uses `jsonschema.FormatChecker`.
- Diff path validation uses normalized POSIX checks rather than raw prefix checks.
- The verifier rejects absolute paths, `..`, empty segments, backslashes, quoted paths, whitespace paths, malformed headers, and paths outside `profiles/<agent>/`.
- Duplicate approving approvers are rejected.
- Pytest coverage was added for valid records, policy thresholds, traversal, malformed diff headers, duplicate approvers, and invalid timestamp formats.
- CI now runs `pytest -q`.

## Branch Protection Note

This PR documents branch protection as a required repository control, but the currently available connector actions in this workflow did not expose a branch-protection read or write API. Branch protection for `main` should therefore be verified manually in GitHub repository settings or by a future tool with branch protection access.

## Attack Review

### Design point: policy is the approval threshold source

Attack: keeping constants in code is simpler.
Defense: duplicated thresholds create drift between policy and enforcement. Code may keep fallbacks for missing policy files, but repository behavior must load policy.
Result: unchanged.

Attack: policy parsing can fail.
Defense: failure should be visible during validation rather than silently using stale constants. This PR keeps conservative fallbacks only for absent policy files.
Result: unchanged.

Attack: per-change thresholds might need exceptions.
Defense: exceptions should be encoded as reviewed policy changes, not hidden in proposal records.
Result: unchanged.

Conclusion: locked for v0.7.

### Design point: reject ambiguous diff paths

Attack: Git supports quoted and whitespace paths, so rejecting them is conservative.
Defense: before any mutation path exists, conservative rejection is safer than partially supporting ambiguous encodings incorrectly.
Result: unchanged.

Attack: string normalization may still miss edge cases.
Defense: the verifier now rejects traversal, absolute paths, backslashes, empty path segments, malformed headers, and non-profile paths. Future apply still requires a dedicated patch applicability gate.
Result: unchanged.

Attack: path-only tests are enough.
Defense: approval and timestamp adversarial cases are also included because future apply depends on the whole record chain.
Result: unchanged.

Conclusion: locked for v0.7.

## Review

- Secret safety: pass. No secret reads were added.
- Runtime safety: pass. No runtime mutation was added.
- Apply boundary: pass. `apply` remains intentionally unimplemented.
- Hermes runtime alignment: pass. This does not replace provider runtime, tools registry, session storage, gateway, cron, or AIAgent.
- Remaining pre-apply work: authenticated approvals, file locks, clean Git state checks, rollback point creation, patch applicability checks, post-apply validation, and branch protection verification.
