# v1.2 Pre-Apply Plan Generation

## Status

Implemented as a non-mutating governance-record generator. `apply` remains disabled.

## Purpose

v1.1 defined the pre-apply safety contract. v1.2 adds a way to generate a schema-valid `pre-apply-plan.yaml` from an existing change record after the existing verification gates pass.

## Command

```bash
python scripts/generate-pre-apply-plan <change_id> --root .
```

By default the command writes:

```text
changes/<change_id>/pre-apply-plan.yaml
```

`--output` is intentionally constrained. When provided, it must resolve to the same canonical path: `changes/<change_id>/pre-apply-plan.yaml`. It cannot be used to write under `profiles/`, runtime directories, or outside the repository. The command refuses to overwrite an existing plan unless `--overwrite` is provided.

## Safety boundary

The generator does not:

- apply patches;
- create locks;
- write runtime state;
- read secret values;
- mutate managed profiles;
- create rollback commits;
- execute business actions.

It writes only a governance plan file under `changes/<change_id>/`.

## Required preconditions

Before writing a plan, the generator runs:

```bash
python scripts/hermes-agentops --root <root> changes verify <change_id> --check-git-clean --check-patch-applicable
```

This reuses the existing verified path for policy, proposal, approvals, rejection, hash binding, path scope, clean target profile state, and patch applicability checks.

## Attack / defense convergence

### Design point: reuse existing verification

Attack 1: A second generator-specific verifier could drift from `changes verify`.
Defense 1: The generator shells out to the existing `changes verify --check-git-clean --check-patch-applicable` path.
Result: unchanged.

Attack 2: A malicious or malformed change could still get a plan if the generator ignores verify failures.
Defense 2: Any non-zero verify result aborts generation and writes no plan.
Result: unchanged.

Attack 3: Future refactors could weaken the generator without changing tests.
Defense 3: Regression tests assert rejected/under-approved changes do not produce a plan.
Result: unchanged.

Converged decision: plan generation must depend on the existing verify path and fail closed.

### Design point: write a plan but not mutate profiles

Attack 1: Writing a file is still mutation.
Defense 1: The only mutation is a governance record under `changes/<change_id>/`; managed profile files and runtime state are untouched.
Result: unchanged.

Attack 2: A generated plan could be mistaken for permission to execute apply.
Defense 2: The schema requires `mutation_enabled: false`, and the generator always emits false.
Result: unchanged.

Attack 3: Overwriting plans could erase evidence.
Defense 3: The generator refuses overwrites by default and requires explicit `--overwrite`.
Result: unchanged.

Attack 4: An arbitrary output path could expand the mutation surface beyond the documented governance record.
Defense 4: `--output` must resolve to the canonical `changes/<change_id>/pre-apply-plan.yaml` path.
Result: unchanged.

Converged decision: generation is allowed only as a non-runtime governance write with explicit overwrite control and a fixed output boundary.

## Deep review checklist

- `apply` remains disabled.
- The generator calls existing verification before writing.
- Failed verification writes no plan.
- The generated plan validates against `schemas/pre-apply-plan.schema.json`.
- `mutation_enabled` is always false.
- The plan path stays under `changes/<change_id>/`.
- `--output` cannot write outside the canonical plan path.
- The command refuses overwrite by default.
- Tests cover success, failed verification, output-boundary rejection, and overwrite protection.
- CI compiles the generator and runs its tests.
