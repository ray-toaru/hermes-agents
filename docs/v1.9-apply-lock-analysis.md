# v1.9 Apply-Lock Analysis

## Status

Implemented as a stdout-only read-only analyzer. This does not enable `apply`, acquire locks, release locks, or write report files.

## Purpose

Individual apply-lock records already describe future exclusive repository locks. The analyzer adds repository-wide visibility before any future real lock implementation exists.

It answers one narrow question: are there lock records that should block future apply attempts until a human reviews them?

## Boundaries

The analyzer must not:

- acquire real locks;
- release real locks;
- mutate lock records;
- delete or rewrite stale locks;
- write generated reports to arbitrary paths;
- apply patches;
- mutate managed profile files;
- mutate runtime state;
- read real secret values;
- execute rollback;
- execute business actions.

`mutation_enabled` in generated reports must remain `false`.

## Output Boundary

Generated reports are printed to stdout. File persistence, if ever needed, requires a separate reviewed governance-report path design rather than arbitrary `--output` writes.

## Blocking Semantics

The analyzer treats these as blocking:

- `active` locks;
- expired `active` locks, reported as `expired_active`;
- `stale` locks;
- `recovery_required` locks;
- invalid or unparsable lock records.

`released` locks are non-blocking.

Expired active locks remain blocking because automatic release is unsafe without human inspection.

## Future Use

A future real lock acquisition command may use this analyzer as a preflight input, but it must still have its own reviewed design for atomic acquisition, release, stale recovery, audit records, and failure handling.
