# v2.10.1 Test Runner Stability Investigation

## Status

Implemented as a test-harness and internal-dispatch hardening slice. It does not enable real apply, does not write production locks, does not release locks, does not mutate profiles, does not execute rollback, does not write production audit records, does not read secret values, does not mutate runtime state, and does not orchestrate business work.

## Problem Observed

During v2.10 local validation, `tests/test_sandbox_recovery_simulation.py` intermittently printed a passing pytest summary and then failed to return cleanly, or stalled during repeated runs. Live process inspection during a stalled run showed active or defunct `git` child processes, including `git cat-file` from rollback-point evidence creation.

The failure was not an assertion failure. It was a process-lifecycle stability issue in sandbox-heavy tests that repeatedly run repository scripts in-process while those scripts spawn Git subprocesses.

## Root Cause

The test helper `tests/agentops_test_utils.py::run_script()` wrapped entire in-process script calls in `SIGALRM`. Repository scripts invoked through that helper may call `subprocess.run()` indirectly through `agentops_common.run_command()`.

An asynchronous `SIGALRM` can arrive while the parent Python process is inside `subprocess.run()` waiting for a Git child. Raising from that signal path can interrupt the wait/cleanup path, leaving child processes defunct or causing pytest to stall after test assertions have already completed.

A related risk existed for `agentops_common.run_internal_python_command()`, which used `run_python_script_main()` with its default in-process timeout even when dispatching subprocess-heavy repository scripts. That could put another `SIGALRM` wrapper around scripts that themselves launch Git.

## Fix

- `tests/agentops_test_utils.py::run_script()` no longer installs a process-wide `SIGALRM` around the whole script.
- `agentops_common.run_internal_python_command()` now dispatches repository-internal scripts with `timeout=0`, avoiding process-wide in-process alarms around subprocess-heavy scripts.
- Direct `run_python_script_main(..., timeout=N)` still supports fail-closed timeout behavior for pure-Python timeout use cases and remains covered by tests.
- `tests/conftest.py` still applies default timeouts to direct test `subprocess.run()` calls and clears any leftover alarm state after each test.
- CI-level grouped pytest commands still run under shell `timeout`, so suite-level hangs remain fail-closed.

## New Regression Coverage

`tests/test_agentops_common.py::test_run_internal_python_command_does_not_alarm_subprocess_heavy_script` verifies that internal dispatch can run a repository-style script that launches a child command through `run_command()` without wrapping the whole call in a SIGALRM timeout.

## Remaining Boundary

This fix is test-runner and internal-dispatch stability only. It does not make any evidence record authoritative, does not change production lock semantics, and does not advance real apply implementation readiness.
