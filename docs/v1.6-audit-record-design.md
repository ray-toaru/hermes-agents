# v1.6 Audit Record Design

## Status

Implemented as a read-only governance validator. This does not enable `apply`.

## Purpose

Audit records capture evidence for the future apply pipeline after pre-apply plan, apply-lock, and rollback-point records exist. They are evidence contracts, not execution authority.

## Boundaries

The audit record validator must not:

- apply patches;
- mutate managed profile files;
- mutate runtime state;
- read real secret values;
- acquire or release real locks;
- execute rollback;
- execute business actions;
- route or orchestrate business tasks.

`mutation_enabled` must remain `false`.

## Record Semantics

An audit record binds:

- `change_id` and `agent`;
- `pre_apply_plan_sha256`;
- `apply_lock_sha256`;
- `rollback_point_sha256`;
- git `head_before` and `head_after`;
- redacted command evidence;
- explicit boundary acknowledgements.

For the current read-only phase, `head_before` must equal `head_after` because validation must not mutate the repository.

## Command Evidence

Command evidence is restricted to a small read-only allowlist, such as schema validators, change verification, `git apply --check`, and tests. The validator rejects shell chaining, redirects, container/service commands, network installers, Git mutation commands, and other unsafe command strings.

This is intentionally conservative. Future mutation auditing requires a separate design and tests.

## Failure Handling

Audit validation failure does not trigger rollback. Recovery remains manual and operator-reviewed.

## Review Notes

- Audit records are not authorization.
- Audit records do not prove reviewer identity.
- Audit records do not release locks.
- Audit records do not make `apply` safe by themselves.
