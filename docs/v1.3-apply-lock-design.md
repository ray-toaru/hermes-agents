# v1.3 Apply Lock Design

## Status

Design and validation only. `apply` remains disabled. This version does not acquire, release, or mutate locks.

## Purpose

A future apply path needs a concurrency guard before any mutation. v1.3 defines the apply-lock governance record and a read-only validator so lock semantics can be reviewed before implementation.

## Implemented in v1.3

- `schemas/apply-lock.schema.json` defines the lock record contract.
- `docs/examples/apply-lock.example.yaml` provides a schema-valid example.
- `scripts/check-apply-lock` validates lock records without creating or releasing locks.
- CI validates the example lock.

## Non-goals

- Do not implement `apply`.
- Do not acquire locks.
- Do not release locks.
- Do not mutate managed profiles.
- Do not read secret values.
- Do not mutate runtime state.
- Do not execute business actions.

## Lock contract

A future lock must be:

1. Repository-scoped.
2. Exclusive.
3. Bound to one `change_id`.
4. Bound to the pre-apply plan hash.
5. Bound to the pre-apply `base_commit`.
6. Time-bounded with `created_at` and `expires_at`.
7. Non-mutating in this phase: `mutation_enabled: false`.
8. Recoverable only after manual review of stale-lock evidence.

## Attack / defense convergence

### Design point: repository-level exclusive lock

Attack 1: Per-agent locks allow two changes to mutate shared repository files concurrently.
Defense 1: Require repository scope for the first future apply implementation.
Result: unchanged.

Attack 2: Shared locks are complex and easy to misuse.
Defense 2: Only `exclusive` mode is accepted.
Result: unchanged.

Attack 3: A future implementation may need narrower locks.
Defense 3: Narrower scopes can be designed later after the repository-wide path is proven safe.
Result: unchanged.

Converged decision: first lock contract is repository-scoped and exclusive.

### Design point: stale-lock handling

Attack 1: A stale lock can permanently block operators.
Defense 1: Require `expires_at` after `created_at`.
Result: unchanged.

Attack 2: Automatically releasing stale locks can erase evidence of partial mutation.
Defense 2: Require `manual_review_required: true` and `stale_lock_action: inspect_before_release`.
Result: unchanged.

Attack 3: A malicious actor could forge a stale lock with mismatched ID.
Defense 3: Validator requires `lock_id == change_id + '_lock'`, schema pattern checks, and plan hash binding.
Result: unchanged.

Converged decision: stale locks are time-bounded but require manual inspection before release.

### Design point: plan hash binding

Attack 1: A lock could be reused for a different plan.
Defense 1: Require `pre_apply_plan_sha256`.
Result: unchanged.

Attack 2: A lock could be created on a different repository state.
Defense 2: Require `base_commit`.
Result: unchanged.

Attack 3: The lock schema itself could be mistaken for apply authorization.
Defense 3: Require `mutation_enabled: false` and keep the checker read-only.
Result: unchanged.

Converged decision: lock records must bind change, plan hash, and base commit while remaining non-mutating.

## Deep review checklist

- `apply` remains disabled.
- Lock checker is read-only.
- Schema requires repository scope and exclusive mode.
- Schema requires `mutation_enabled: false`.
- Validator checks timestamp ordering.
- Validator checks `lock_id == change_id + '_lock'`.
- Lock records bind change ID, plan hash, and base commit.
- Stale locks require manual inspection before release.
- CI validates the example lock.
- Rollback is a simple PR revert because no runtime state is mutated.
