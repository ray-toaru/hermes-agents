# v1.4 Apply Lock Acquisition Record

## Status

Implemented as a constrained governance-record write. `apply` remains disabled.

This version does not acquire an operating-system lock, does not release locks, does not apply patches, and does not mutate managed profiles or runtime state.

## Command

```bash
python scripts/acquire-apply-lock <change_id> --root .
```

The command writes exactly one canonical file:

```text
changes/<change_id>/apply-lock.yaml
```

## Preconditions

The command fails closed unless all of these are true:

1. `changes/<change_id>/pre-apply-plan.yaml` exists.
2. The pre-apply plan validates against schema and cross-field checks.
3. The plan path is canonical.
4. The plan `base_commit` equals current Git `HEAD`.
5. No existing `changes/*/apply-lock.yaml` with status `active`, `stale`, or `recovery_required` exists.
6. An existing `active` lock whose `expires_at` is in the past is treated as stale and blocks creation.
7. The output file does not already exist.
8. The generated lock validates against `schemas/apply-lock.schema.json`.
9. The generated lock `pre_apply_plan_sha256` equals the actual bytes of the canonical pre-apply plan.

Released locks under other change directories do not block new lock creation. A released lock at the same canonical output path still blocks by file-existence because overwriting lock evidence would erase history.

## Safety boundary

The command does not:

- implement or call `apply`;
- mutate managed profiles;
- mutate runtime state;
- read or print real secret values;
- release or delete locks;
- execute business actions.

It only writes a governance record under `changes/<change_id>/`.

## Attack / defense convergence

### Design point: lock record is not mutation authority

Attack 1: The word "acquire" could be mistaken for permission to apply.
Defense 1: The command writes only a record with `mutation_enabled: false`; `apply` remains non-zero.
Result: unchanged.

Attack 2: A lock record could be used without verifying the plan.
Defense 2: Creation requires a valid canonical pre-apply plan and binds to its SHA-256 bytes.
Result: unchanged.

Attack 3: A plan could become stale after generation.
Defense 3: The command refuses if plan `base_commit` differs from current `HEAD`.
Result: unchanged.

Converged decision: creating an apply-lock record is an apply-adjacent governance step, not execution authority.

### Design point: repository-wide blocking locks

Attack 1: Per-change checks miss another active lock in the repository.
Defense 1: Creation scans `changes/*/apply-lock.yaml`.
Result: unchanged.

Attack 2: Expired active locks could be ignored automatically.
Defense 2: Expired active locks are treated as stale and require manual review.
Result: unchanged.

Attack 3: Released locks should not block unrelated work.
Defense 3: Released locks under other changes do not block; same-path overwrite is still refused to preserve evidence.
Result: unchanged.

Converged decision: active/stale/recovery locks block globally; released locks do not block unrelated changes.

## Deep review checklist

- `apply` remains disabled.
- Lock creation writes only `changes/<change_id>/apply-lock.yaml`.
- Missing or invalid plan blocks creation.
- Plan hash is computed from actual file bytes.
- Plan `base_commit` must match current `HEAD`.
- Existing active/stale/recovery locks block creation.
- Released locks do not block unrelated changes.
- Existing same-path lock file is never overwritten.
- CI compiles the script and tests success/failure cases.
- Rollback is a PR revert because no runtime state is mutated.
