# v1.8 Post-Apply Validation Evidence

## Status

Implemented as a read-only governance validator. This does not enable `apply`.

## Purpose

Post-apply validation evidence records define the contract for proving that a future operator-reviewed mutation was followed by validation. This layer is intentionally only an evidence validator: it does not perform apply, rollback, service restart, runtime mutation, or business execution.

## Boundaries

The post-apply validation validator must not:

- apply patches;
- mutate managed profile files;
- mutate runtime state;
- read real secret values;
- acquire or release real locks;
- execute rollback;
- execute business actions;
- route or orchestrate business tasks.

`mutation_enabled` must remain `false` because the validator itself is read-only.

## Record Semantics

A post-apply validation evidence record binds:

- `change_id`;
- `agent` from the change id;
- `audit_record_sha256`;
- `expected_head`;
- `actual_head`;
- validation command evidence;
- explicit read-only boundary acknowledgements.

For `status: success`, `actual_head` must equal `expected_head` and all validation commands must succeed. For `status: failed`, the record must include either a head mismatch or failed command evidence.

When `--require-audit-file` is used, the validator requires a matching `changes/<change_id>/audit-record.yaml` file hash.

## Review Notes

- This is validation evidence, not authorization.
- This does not make future apply safe by itself.
- This does not execute rollback on failure.
- Future mutation still requires real lock acquisition/release, rollback creation, authenticated approvals, and failure recovery design.
